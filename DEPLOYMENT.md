# Deploying EduConnect

The app is two pieces that deploy separately:

| Piece | Host | Why |
| --- | --- | --- |
| Frontend (React/Vite) | **Cloudflare Pages** | Static build — Pages serves it well |
| Backend (Express) | **Render** | Needs a real Node runtime |
| Database | **MongoDB Atlas** | No host can reach `127.0.0.1` on your laptop |

> **Why not Cloudflare for the backend?** Workers run on V8 isolates, not Node.
> Express needs Node's `http` module, and Mongoose opens raw TCP sockets — neither
> works there. Hyperdrive accelerates Postgres/MySQL, not MongoDB. Running the API
> on Cloudflare would mean rewriting it (Express→Hono, MongoDB→D1, bcrypt/JWT→Web Crypto).

Do the steps in order — each one produces a value the next needs.

---

## 1. Push to GitHub

The repo is already committed locally. You need to authenticate once.

**Option A — GitHub CLI (easiest)**

```bash
winget install --id GitHub.cli     # then reopen your terminal
gh auth login                      # choose GitHub.com → HTTPS → browser
cd d:/EduConnect
gh repo create EduConnect --private --source=. --remote=origin --push
```

**Option B — create the repo in the browser**

1. Go to <https://github.com/new>, name it `EduConnect`, set **Private**, create it
   with no README/.gitignore/licence.
2. Then:

```bash
cd d:/EduConnect
git remote add origin https://github.com/<your-username>/EduConnect.git
git push -u origin main
```

Git will prompt for credentials — use a
[personal access token](https://github.com/settings/tokens) as the password.

---

## 2. MongoDB Atlas (database)

1. Create a free account at <https://www.mongodb.com/cloud/atlas/register>.
2. Create a free **M0** cluster.
3. **Database Access** → add a user, note the username/password.
4. **Network Access** → Add IP → *Allow access from anywhere* (`0.0.0.0/0`).
   Render's outbound IPs are dynamic, so this is required on the free tier.
5. **Connect → Drivers** → copy the connection string. It looks like:

```
mongodb+srv://USER:PASSWORD@cluster0.xxxxx.mongodb.net/educonnect?retryWrites=true&w=majority
```

Replace `USER`/`PASSWORD` and make sure `/educonnect` is in there as the db name.
Keep this string — it's `MONGODB_URI` in the next step.

---

## 3. Backend on Render

1. Sign in at <https://render.com> with GitHub.
2. **New → Blueprint**, pick your `EduConnect` repo. It reads `render.yaml`.
3. Render will prompt for the three secrets it won't store in git:
   - `MONGODB_URI` → the Atlas string from step 2
   - `OPENAI_API_KEY` → your key (see the warning at the bottom of this file)
   - `CLIENT_URL` → leave as `http://localhost:5173` for now; you'll correct it in step 5
4. Deploy. You'll get a URL like `https://educonnect-api.onrender.com`.
5. Check it: `https://educonnect-api.onrender.com/api/health` → `{"status":"ok"}`

`ACCESS_TOKEN_SECRET` and `REFRESH_TOKEN_SECRET` are generated by Render
automatically — you never see or set them.

> **Free tier caveat:** the service sleeps after ~15 min idle. The first request
> after that takes 30–60 s to wake. Fine for a demo, not for real users.

---

## 4. Frontend on Cloudflare Pages

1. Sign in at <https://dash.cloudflare.com> → **Workers & Pages → Create → Pages
   → Connect to Git** → pick the repo.
2. Build settings:

   | Field | Value |
   | --- | --- |
   | Framework preset | Vite |
   | Build command | `npm run build` |
   | Build output directory | `dist` |
   | Root directory | `frontend` |

3. **Environment variables** → add:

   ```
   VITE_API_BASE = https://educonnect-api.onrender.com/api
   ```

   (your Render URL from step 3, with `/api` on the end)

4. Save and deploy. You'll get `https://educonnect.pages.dev`.

`public/_redirects` is already in the repo so client-side routes like `/schedule`
resolve instead of 404ing.

---

## 5. Connect the two (don't skip — login breaks without it)

Back in **Render → your service → Environment**, set:

```
CLIENT_URL = https://educonnect.pages.dev
```

Save — Render redeploys. This does two things:

- lets the API accept browser requests from your Pages domain (CORS)
- allows credentialed requests, so session cookies actually work

`COOKIE_SAMESITE=none` and `COOKIE_SECURE=true` are already set in `render.yaml`.
Both are mandatory: with the frontend and API on different domains, browsers
discard `SameSite=Lax` cookies and you'd get logged out on every request.

---

## 6. Verify

Open your Pages URL and check:

- [ ] Register a new account → lands on the dashboard
- [ ] Reload the page → still logged in (proves cookies survive cross-site)
- [ ] Add a schedule event → persists after reload
- [ ] Ask the tutor something → reply comes back
- [ ] Log out → redirected to login

If login appears to work but you're logged out on reload, `CLIENT_URL` is wrong
or `COOKIE_SAMESITE` isn't `none`. Check the browser devtools **Application →
Cookies** tab for `ec_access`.

## Environment variables

**Backend (Render)**

| Variable | Value |
| --- | --- |
| `NODE_ENV` | `production` |
| `MONGODB_URI` | Atlas connection string |
| `ACCESS_TOKEN_SECRET` | auto-generated |
| `REFRESH_TOKEN_SECRET` | auto-generated |
| `COOKIE_SECURE` | `true` |
| `COOKIE_SAMESITE` | `none` |
| `OPENAI_API_KEY` | your OpenAI key |
| `CLIENT_URL` | your Pages URL |

**Frontend (Cloudflare Pages)**

| Variable | Value |
| --- | --- |
| `VITE_API_BASE` | `https://<render-url>/api` |

## ⚠️ Rotate your OpenAI key first

The key currently in `backend/.env` has been sitting in plaintext on disk. It is
gitignored and was **not** committed, but before putting it into a hosting
provider you should rotate it:

1. <https://platform.openai.com/api-keys> → revoke the old key
2. Create a new one, and set a **usage limit** on the project
3. Use the new key for `OPENAI_API_KEY` on Render — never in a committed file

Both `/api/chatbot` and `/api/quiz/generate` require a logged-in user and are
rate-limited, but anyone who registers can spend your OpenAI credit.
